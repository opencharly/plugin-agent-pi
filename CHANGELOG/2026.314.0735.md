# 2026.314.0735 — refactor(schema): derive the pi word sets from vocabulary tables

## Summary

Convert the five inline `|` word unions in `candy/plugin-agent-pi/schema/pi.cue`
to the §10.1 S3 vocabulary-table idiom, so each closed set of words has ONE home
and the enum a document meets is `or()` of that table's keys:

```
_commandType  _streamingBehavior  _mode          (+ _commandTypeWord / _streamingBehaviorWord / _modeWord)
```

That is the 13 `union` rows `design/dpat-baseline.tsv` records for
`plugin-agent-pi/candy/plugin-agent-pi/schema/pi.cue`. **They are FIVE
disjunctions, not 13:** the 32-word Pi RPC command catalog is written one
alternative per line (9 rows), and `streamingBehavior`, the command `mode`, the
state `steeringMode` and the state `followUpMode` are each written on one line
(4 rows). The catalog's last word, `extension_ui_response`, closes its line after
a `|`, so it carries a row too — which is why the catalog is 9 rows for 32 words.

**One extraction beyond the field-by-field kind.** Pi renders ONE two-word enum
in three fields: the command `mode` and the state `steeringMode` / `followUpMode`
all accept `all | one-at-a-time`. Two tables for that would be a copy, so `_mode`
is ONE table and all three fields are `or(_modeWord)` — extracted on the second
occurrence, per R2. A later divergence of any one field is then one table split,
not three literals to find.
